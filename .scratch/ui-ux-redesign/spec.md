# 前端 UI 与交互体验全面重构规范 (UI/UX Redesign)

Status: ready-for-agent

## Problem Statement

当前 SongRoom 的功能状态机与底层调度已经完备，但前端界面与交互存在严重的“开发规约驱动”和“技术实现细节外露”痕迹，导致日常协作点歌体验杂乱、生硬且心智模型混乱：

1. **信息噪音严重与技术细节过度裸露**：
   - 界面充斥着冗长的背景解释、免责条款和系统规约说明（如在每个表单和卡片下罗列长段规则说明，危险操作弹窗中罗列多条排比句），信噪比极低；
   - 未登录首页挂着巨大的“应用已准备就绪”运维看板，甚至带有“功能正在交付”等临时开发期字样；
   - 公共歌单主页面被一个巨大的卡片占据半屏，网易云歌单 ID、同步时间、同步状态等技术信息压倒了核心业务，歌曲列表被挤在下半截；
   - 界面上同时存在“刷新歌单”（触发后端向网易云同步）和“更新状态”（前端重新读取本地接口）两个按钮，将系统内部的实现机制强加给用户理解；
   - 已删除房间的底层歌单清理进度长期堆砌在房间列表底部，严重污染核心视觉。

2. **工作台布局失调与主内容无法居中**：
   - 进入房间后的工作台采用了生硬的固定侧栏机制，导致主内容在大屏上严重偏左、两侧留白不均，无法舒展居中；
   - 手机竖屏下侧边栏生硬堆在文档流最上方，用户每次进入房间或切换标签都要滑过几屏的非核心信息，才能看到歌单。

3. **导航链路冗余与操作死胡同**：
   - 用户登录后默认停留在房间列表，顶部导航栏右上角仍常驻“我的房间”文字链接，点击毫无意义；
   - 账号设置等二级页面缺少明确的返回入口，成为单向死胡同；
   - 顶部导航栏被大号服务状态指示徽章抢占视觉焦点。

4. **心智模型混淆与交互摩擦**：
   - 歌单正上方的搜索框让用户第一眼误以为是“过滤当前歌单已有歌曲”，敲击回车却发起了全网网易云点歌，搜索候选还遮挡歌单；
   - 房间成员页面将大号邀请码卡片和审批管理卡片长期置顶，真正的成员列表被挤在最下方；
   - 新用户刚进入时缺乏清晰的房主建房与室友免绑加入的双轨分流引导；
   - 创建房间表单中设置了不必要的二次复选框；
   - 点歌提交缺乏即时的微动效与正反馈。

5. **视觉设计质感欠缺（Generic AI Slop）**：
   - 页面依赖平铺灰白背景与单一荧光紫色，卡片扁平单调，缺乏呼吸感、景深阴影与精致的层次。

## Solution

遵循“内容为王、消除细节外露、高信噪比与现代声学设计”的原则，对整个前端进行全面的 UI/UX 重构：

1. **专业视觉系统与 Design Tokens**：
   - 引入专业声学基调配色，告别粗暴荧光紫；建立微弱景深阴影（Colored subtle shadows）、微光边框与严谨字阶；全站数字与时间启用 `tabular-nums`。

2. **全局 AppShell 与导航链路重构**：
   - 顶部导航栏移除重复的“我的房间”链接，升级为紧凑优雅的用户身份胶囊（支持直达账号设置与退出）；
   - 弱化大号服务状态为微型指示灯；
   - 账号设置等二级页面补齐显式返回按钮，消除导航死胡同。

3. **现代 App 双栏居中工作台**：
   - 彻底废除旧式固定定位，采用标准弹性双栏架构：左侧为吸附式 Sidebar（房间名、身份徽章、垂直 Tab），右侧为主工作区；
   - 主工作区内部容器限定最大宽度并严格居中，使公共歌单与成员面板在视口中绝对居中呈现；
   - 移动端自适应为底部固定导航栏（Bottom Navigation Bar），契合大拇指单手操作热区。

4. **公共歌单与点歌心智模型彻底解耦**：
   - 拆除大号外层卡片，收拢网易云 ID 与技术元数据，让歌曲列表占据 80% 以上的第一视觉；
   - 消除暴露实现细节的双按钮，合并为单一的“同步歌单”操作；
   - 歌单上方不再常驻易混淆的直接搜索框，改为显眼的「+ 点歌」按钮，呼出专用的网易云点歌抽屉/面板，彻底区分歌单内查找与全网点歌；
   - 歌曲列表采用现代音乐流媒体排版（序号、歌名歌手专辑分层、右侧点歌人胶囊徽标、高质感空歌单引导），点歌操作伴随微动效与 Toast 反馈。

5. **全站系统级大降噪与弹窗/表单重塑**：
   - 确立“静默即正常、异常才反馈”原则：未登录首页彻底移除大号运维监控卡片与开发期临时文案；
   - 全站表单彻底消灭常识教导与规约说教（如“账号称呼可以修改并允许重复”等），统一用简洁占位符（Placeholder）替代辅助长句，异常时才内联反馈；
   - 全站危险确认弹窗（Radix AlertDialog）彻底废除排比后果清单与调试版本号，采用「动宾标题 + 核心单句风险 + 关键危险标签」的极简高信噪比范式；
   - 房间设置等页面坚决消灭左脚踩右脚的冗余只读信息镜像陈列；
   - 房间成员界面以成员列表为主体，邀请功能收敛为右上角按钮/弹窗，待审批申请仅在有待处理时作为轻量通知横幅浮现并在抽屉审批。

6. **新用户双轨引导与多平台扩展架构**：
   - 房间列表空状态提供“创建新房间（房主）”与“加入已有房间（室友免绑定）”双轨分流卡片；
   - 将已删除房间的歌单清理进度从房间列表移出，收归账号高级设置；
   - 创建房间移除强制多余的复选框；
   - 账号绑定与建房选择面向未来多平台（QQ/汽水/酷狗）扩展，抽象为“音乐平台账号选择器”。

## User Stories

### 全局导航与视觉体验
1. 作为登录用户，我希望在顶部导航栏右上角看到直观的用户身份胶囊，以便快速访问账号设置或退出登录。
2. 作为登录用户，我希望顶部导航栏不要出现多余的“我的房间”文字链接，以便在浏览房间列表时不产生导航困惑。
3. 作为登录用户，我希望 Header 上的服务状态指示保持极简低调，以便不干扰我对核心业务的注意力。
4. 作为访问者，我希望全站交互元素拥有平滑舒适的悬停和按压视觉反馈，以便获得现代应用的品质感。
5. 作为浏览大量歌曲与时间数据的用户，我希望数字和时间对齐整齐（tabular-nums），以便清晰阅读排版。
6. 作为从房间列表进入账号设置的用户，我希望页面顶部有清晰的返回按钮，以便随时顺畅返回房间列表。
7. 作为查看账号设置的用户，我希望个人资料、密码安全、音乐平台授权和高级清理按清晰的模块化卡片分布，以便一目了然。

### 房间工作台与布局
8. 作为在桌面电脑上操作房间的用户，我希望左侧拥有稳固清晰的侧边导航栏，以便随时感知当前房间名、我的角色和快速切换功能。
9. 作为在桌面电脑上操作房间的用户，我希望右侧的主工作区内容在视口中舒适居中，以便在宽屏显示器上获得对称呼吸的视觉感受。
10. 作为在手机端访问房间的用户，我希望功能导航位于屏幕底部大拇指热区，以便单手舒适切换歌单、成员与设置。
11. 作为在手机端访问房间的用户，我希望进入房间后第一眼看到的是核心歌单内容，以便无需滑过长段头部信息即可开始听歌点歌。
12. 作为在移动设备上输入内容的用户，我希望软键盘弹起时不破坏工作台布局与视口滚动，以便流畅输入。

### 公共歌单与点歌
13. 作为进入公共歌单的成员，我希望第一眼看到的是精美的歌曲列表，以便立刻了解当前房间有哪些歌曲。
14. 作为公共歌单查看者，我希望技术性的网易云歌单 ID 和长段状态文本被收拢，以便不占用宝贵的列表展示空间。
15. 作为希望获取最新歌单的成员，我希望点击单一的“同步歌单”按钮即可完成拉取，以便无需理解前端缓存与服务端同步的区别。
16. 作为正在同步歌单的成员，我希望看到轻量的旋转刷新指示，并在同步完成后获得即时反馈，以便明确知道状态已更新。
17. 作为想要点歌的房间成员，我希望点击醒目的「+ 点歌」入口展开专属点歌面板，以便明确知道自己在从外部音乐平台向房间点歌。
18. 作为点歌人，我希望在点歌面板中输入歌名或歌手并清晰查看候选列表，以便准确挑选想要听的版本。
19. 作为点歌人，我希望点歌成功后获得明确的 Toast 反馈，且新加入的歌曲在公共歌单中平滑高亮呈现，以便获得及时的成就感。
20. 作为遇到网络或限流情况的点歌人，我希望看到温和易懂的排队或稍候提示，以便不被生硬的错误代码困扰。
21. 作为浏览公共歌单的成员，我希望每首歌曲右侧清晰展示带有昵称的点歌人胶囊徽标，以便一眼认出是谁点的歌。
22. 作为进入尚无歌曲的公共歌单的成员，我希望看到充满音乐氛围的精致空状态引导，以便受鼓舞主动发起第一次点歌。

### 房间成员与审批
23. 作为进入“房间成员”页面的成员，我希望首先看到的是整洁美观的成员列表，以便快速查看房间内现有哪些室友。
24. 作为需要邀请室友的成员，我希望点击右上角的「邀请室友」按钮呼出分享弹窗，以便快速复制邀请码或邀请链接。
25. 作为房主，我希望在平时不看到常驻的审批大卡片，以便界面保持纯净。
26. 作为房主，我希望在有新室友申请加入时，在成员列表顶部看到轻量醒目的提示条，以便及时获知并一键审批。
27. 作为房主，我希望在抽屉或轻量浮层中审批申请，以便无需离开成员列表上下文即可完成通过或拒绝。
28. 作为查看特定成员详情的用户，我希望以抽屉或内联展开方式查看，以便不打断原列表的滚动位置。

### 全站表单与说明文案降噪
32. 作为填写表单的用户，我希望输入框下方不出现冗长常识性说明文字，以便界面干净通透。
33. 作为输入各项字段的用户，我希望长度和格式要求直接通过占位符提示，以便一目了然。
34. 作为访问房间设置的用户，我希望不要重复陈列侧边栏已有的只读信息，以便快速聚焦可操作项。
35. 作为进行破坏性操作的用户，我希望确认弹窗展示单句核心风险与明确警示标签而非冗长排比清单，以便迅速做出明确决断。

### 房间创建与设置
36. 作为准备创建房间的房主，我希望表单顶部清晰展示用于建房的音乐平台账号，以便明确授权主体。
37. 作为准备创建房间的房主，我希望无需勾选多余的确认复选框，以便填写完房间名和昵称后一气呵成完成创建。
38. 作为规划接入多个音乐平台的用户，我希望在创建房间时可以从已绑定的平台账号中选择，以便为未来多平台留出自然的操作路径。
39. 作为访问房间设置的用户，我希望基本信息、关联音乐账号与危险操作被清晰模块化分区，以便安全管理。

### 首页与房间列表引导
40. 作为首次访问点歌台的新访客，我希望在首页看到突出宿舍协作与音乐共享的产品介绍，以便建立良好的第一印象。
41. 作为正常使用服务的用户，我希望在首页不被大号技术就绪状态卡片打扰，以便专注登录或注册。
42. 作为刚注册尚未拥有房间的房主，我希望在空房间列表看到醒目的“创建我的房间”行动卡片，并在未授权时顺畅引导去授权。
43. 作为受邀加入的新室友，我希望在空房间列表看到明确的“加入已有房间”卡片，并获知无需绑定音乐账号，以便消除操作顾虑。
44. 作为拥有多个房间的用户，我希望在房间卡片上直观看到我的角色（房主/室友）和房间状态，以便快速选择进入。
45. 作为曾经删除过房间的用户，我希望歌单底层清理进度收归账号高级设置中，以便不污染我的日常房间列表。

### 室友加入与申请跟踪
46. 作为收到邀请链接的室友，我希望打开时看到像邀请函一样的目标房间信息，以便确信自己正在加入正确的房间。
47. 作为已提交加入申请的室友，我希望在状态跟踪页看到清晰直观的审批步骤时间轴，以便了解当前审核进度。
48. 作为等待审批的室友，我希望在房主批准后页面能感知并自动引导进入房间，以便获得丝滑的入房体验。

## Implementation Decisions

### 1. 全局设计规范与 Tokens 体系
- **色彩与材质**：
  - 弃用单一生硬的荧光纯紫与纯灰底色；
  - 确立统一的现代调色板：深邃稳健的基底中性色阶（Neutral Slate）、温润的表面背景色、低饱和度且富质感的主题强调色（Accent Indigo/Violet）；
  - 引入 1px 微光边框（Subtle Border）与多阶彩色环境阴影（Tinted ambient shadows），营造细腻的卡片层次感。
- **字体排版**：
  - 全局优化字阶与行高；Display 标题减小字间距增强力量感，Body 正文确保舒适行高与阅读宽度；
  - 英文、数字、歌单 ID 及时间统一配置 `tabular-nums` 等宽特性。
- **微交互标准**：
  - 全局按钮与可交互卡片建立标准的 150~200ms cubic-bezier 平滑过渡；
  - 提供微妙的 `:active` 缩放/形变触感（scale: 0.985），增强按压确认感。

### 2. 全局 Shell 与导航重构
- **Header 架构**：
  - 左侧保留精致 Brand 标识；
  - 移除已登录状态下右上角的“我的房间”文字链接；
  - 右侧统一为用户身份胶囊（User Capsule）：展示用户缩写/头像与称呼，点击/悬停展示下拉菜单（“账号设置”、“退出登录”）；
  - 将原有的 `HealthStatus` 大号胶囊降级为极简指示点，仅在服务异常时才展示提示。
- **二级页面返回体系**：
  - 账号设置页面 (`AccountPage`)、创建房间页面等二级路径均在页面头部提供统一的带箭头返回链接，支持返回上一页或兜底房间列表，杜绝操作死胡同。

### 3. 房间工作台居中布局与移动端适配
- **布局模型重塑**：
  - 彻底移除 `position: fixed` 结合 `calc` 和内边距偏移的脆弱方案；
  - 重构为标准的现代两栏 Flex / Grid 容器：
    - 左侧固定吸附栏：固定宽度（220~240px），放置返回入口、房间名与角色徽章、垂直 Tab 切换；
    - 右侧主工作区：自适应占据剩余宽度，内部页面容器设定 `max-width: 860px; margin: 0 auto;`，保证所有 Tab 的核心内容在右侧工作区内绝对居中。
- **移动端 Ergonomics**：
  - 在视口小于 768px 时，左侧栏折叠，核心导航转为底部固定导航栏（Bottom Navigation Bar），按大拇指热区排布“公共歌单”、“房间成员”、“房间设置”三大入口；
  - 顶部仅保留紧凑的房间信息条，第一视口直接呈现核心内容。

### 4. 公共歌单与点歌心智模型解耦
- **歌单头部信息降噪**：
  - 拆除包围歌单的外层大号卡片，重构为极简 Header：左侧展示歌单名称与歌曲总数徽标，右侧展示极简的同步时间与单点刷新按钮；
  - 将“网易云歌单 ID”等底层技术参数收拢至右上角信息提示气泡（Tooltip）或“房间设置”中。
- **操作合并**：
  - 彻底移除前端的“更新状态”按钮；
  - 保留唯一的“同步歌单”操作，用户触发后由后端拉取上游快照，结合 SSE 事件流自动完成视图刷新；
  - 状态以行内微文字呈现。
- **独立点歌抽屉与面板**：
  - 歌单正上方不再常驻输入框，改为操作栏右上角醒目的 **「+ 点歌」** 按钮；
  - 点击呼出专用的网易云点歌抽屉/面板，包含搜索框、候选单曲列表、选歌试听/提交；
  - 点歌成功后弹出 Toast 提示，自动收起面板，并在歌单列表中高亮新加入歌曲；

### 5. 全站系统级信息降噪与文案规范

## Testing Decisions

### 什么是好的测试
- **仅测试外部可见行为**：只测试用户在界面上能看到的元素、能点击的按钮、产生的导航跳转、屏幕阅读器可访问性（a11y）以及 API 交互反馈；严禁对内部 CSS class 名的细枝末节或组件内部私有状态做过拟合断言。
- **覆盖核心用户主路径**：确保登录、进房、居中展示、点歌提交、成员审批与退出等端到端路径在视觉重构后完好无损。

### 最高测试切缝（Highest Seam）
- **Playwright 端到端浏览器测试（E2E）**：作为整个前端功能与交互的最顶层切缝，全量运行 `apps/songroom/tests/e2e/` 中的测试集。
- **axe-core 自动化无障碍扫描**：通过现有的 `security-a11y-matrix.spec.ts`，验证所有重构后的页面遵循 WCAG 2.1 AA 标准。
- **Vitest 单元与集成测试**：验证客户端核心 hooks（如 `useEventStream`）及公共契约。

## Out of Scope

1. **后端 API 与数据库架构**：本次重构仅涉及前端 SPA 呈现与交互，不变更任何后端 Fastify 路由、Drizzle Schema 或数据库版本。
2. **多音乐平台后端接入**：本次仅在前端 UI 层面完成音乐平台授权选择器的布局抽象与预留，不编写 QQ 音乐、汽水音乐等新平台的实际后端爬虫或 SDK。
3. **引入重型第三方组件库或 CSS 框架**：严格遵循项目原则（优先现有依赖），继续使用现有的 React 19、原生 CSS、Lucide 图标与 Radix UI，不安装 Tailwind 或其他庞大 UI 库。
4. **云端歌曲真实播放器**：点歌台依然遵循快照与协作点歌定位，不实现网易云音频流内嵌播放器。

- 所有改动以保证 E2E 绿色通过为交付硬性指标。
