# 随机点歌首数滚轮选择器规格 (Random Song Count Wheel Picker Spec)

## Problem Statement

目前点歌台的“随机点歌”功能仅支持固定的 5 首、10 首、15 首、20 首四个选项，且默认值为 10 首。对于宿舍听歌或多人聚会场景，20 首（约 1 小时播放量）仍然偏少，无法满足更长时间连续播放或更丰富曲库抽选的需求；同时固定 4 档单选按钮缺乏自由度，无法按需指定如 25 首、30 首或 45 首等自定义歌曲数量。此外，固定的按钮组占据水平空间，未能充分利用现代移动设备的手势滑动以及桌面端的鼠标滚轮操作习惯。

## Solution

将随机点歌的首数选择范围扩展为 10 到 50 首连续正整数，默认首数调整为 20 首。在界面交互上，摒弃原先拥挤死板的固定单选按钮，引入拟物化的 iOS 滚轮桶选择器（Wheel Picker）：视窗居中高亮显示当前选中数值（配“首”单位），上下半透明渐隐展示相邻数字；桌面端支持光标悬停滚动鼠标滚轮平滑增减，移动端支持手指上下触控滑动并自动通过 CSS 吸附对齐到整数字，同时提供严格的滚轮与触摸事件防穿透隔离，不触发外部弹窗晃动。

## User Stories

1. 作为房主，我希望打开随机点歌弹窗时默认期望首数为 20 首，以便在不进行额外调整时也能快速生成时长更适中的歌单。
2. 作为房主，我希望能够在 10 到 50 首之间自由选择任意目标歌曲数量，以便根据本次宿舍聚会或听歌的具体时长灵活设定播放量。
3. 作为桌面端房主，我希望将鼠标指针悬停在首数选择区域直接滚动鼠标滚轮，以便快速、连续且自然地增减目标首数。
4. 作为移动端房主，我希望用手指直接在首数滚轮区域上下拨动，以便获得类似 iOS 闹钟选择器那样顺畅带有惯性的触控体验。
5. 作为房主，我希望在滚轮或手指滑动停止时，控件能自动吸附对齐到最近的整数字，以便明确当前所选的具体首数。
6. 作为房主，我希望滚轮区域在视窗中心高亮展示当前数值，并在上下两侧渐隐相邻数值，以便直观感知滚轮桶的物理形态和前后数值。
7. 作为房主，我希望在首数滚轮滚动到最小值（10）或最大值（50）边界时拦截滚动穿透，以便不会误触背后的弹窗或页面上下晃动。
8. 作为移动端房主，我希望在操作首数滚轮时不会唤起系统软键盘，以便弹窗保持稳定居中而不被输入法遮挡或顶飞。
9. 作为房主，我希望服务端接口严格校验所请求的首数必须在 10 到 50 的整数范围内，以便非法或超限请求能够被安全拦截。
10. 作为房主，我希望无论选择的是否为 5 的倍数（如 23 首），公平抽选算法都能在所选成员间尽量均分并随机打散，以便所有参与成员得到公平体现。
11. 作为房主，我希望在所选成员候选歌曲总量少于所选首数时，界面据实反馈实际抽选数量与差额说明，以便在知情前提下确认替换。
12. 作为房主，我希望预览界面明确标示实际抽选歌曲数与目标首数，以便清晰掌握抽选结果与预期的对比。
13. 作为房主，我希望在关闭或重开随机点歌弹窗时，首数选择器能重置回默认 20 首，以便每次抽选均处于稳定预期的初始状态。
14. 作为使用键盘或屏幕阅读器的用户，我希望滚轮控件具备标准的微调器（spinbutton）语义并响应上下箭头按键，以便无障碍地微调首数。

## Implementation Decisions

- **契约与数据模型扩展**：
  - 前后端契约中，将随机换歌预览命令中的 `count` 字段从原先枚举字面量联合 `5 | 10 | 15 | 20` 调整为 `z.number().int().min(10).max(50).default(20)`。
  - 服务端存储对象 `StoredRandomPreview` 的 `targetCount` 字段类型由固定字面量调整为 `number`。
  - 公平抽选算法接口保持对任意整数目标首数的支持，严格沿用均分、余数随机、去重、交叉归属调整及整组洗牌逻辑。
- **iOS 风格滚轮桶选择器组件（Wheel Picker）**：
  - 移除原弹窗中 `COUNT_OPTIONS = [5, 10, 15, 20]` 单选按钮组。
  - 封装轻量原生 `WheelPicker` 组件：
    - 垂直可视区域高度固定为约 3 行高度（108px ~ 120px），中心行配置高亮指示框与“首”单位标签。
    - 容器应用 CSS `scroll-snap-type: y mandatory`，每个数字条目配置 `scroll-snap-align: center`，由浏览器原生引擎驱动平滑惯性滑动与吸附。
    - 上下边缘应用基于 CSS 的渐变遮罩（`mask-image` 或半透明遮罩背景），呈现拟物滚轮桶的弧面弱化效果。
    - 桌面端监听 `onWheel` 事件，将滚轮垂直滚动映射为数值步进或内部平滑滚动，并结合防抖/节流确保数值吸附更新。
    - 配置 `overscroll-behavior: contain` 并在到达 10 和 50 边界时调用 `preventDefault` / `stopPropagation`，杜绝滚轮事件穿透引起父级容器或页面晃动。
    - 支持无障碍标准：容器标记 `role="spinbutton"`，绑定 `aria-valuenow`、`aria-valuemin="10"`、`aria-valuemax="50"`、`aria-label="期望抽选首数"`，支持上下方向键单步增减。
  - 纯手势操作设计：不提供数字点击唤起文本输入框的逻辑，杜绝移动端软键盘弹起引起的视窗错位。
- **无新依赖原则**：
  - 严格遵守核心原则 4，不引入任何第三方轮子组件库或手势库，基于原生 HTML 滚动、CSS Scroll Snap 与标准 React 事件受控实现。

## Testing Decisions

- **良好测试准则**：只测试系统外部契约与可见交互行为（HTTP 响应状态码、DOM ARIA 状态、数值同步、抽选结果与网易云批量写入），不测试组件内部临时滚动偏移量或私有变量。
- **契约与 API 测试**：
  - 验证 `POST /api/rooms/:roomId/public-playlist/random-preview` 接收合法值（10、20、37、50）成功返回预览，缺省 `count` 时默认为 20。
  - 验证低于 10（如 5、9）、高于 50（如 51、100）或非整数首数被 400 校验拦截拒绝。
- **服务端领域与抽选测试**：
  - 验证 `PublicRandomPreview` 在 10~50 任意首数下的抽选与快照依据持久化，更新受影响的既有集成测试用例。
- **端到端测试（Playwright E2E）**：
  - 桌面端模拟滚轮滚动或按键调整首数，验证中心数值更新与 ARIA 状态同步。
  - 移动端视窗下模拟 touch 拖拽滑动，验证吸附对齐到目标整数。
  - 验证首数达到 10 与 50 时的边界拦截，验证默认 20 首生成预览、候选不足差额提示以及确认批量替换全流程。
- **测试参考（Prior Art）**：
  - API 测试参考 `apps/songroom/src/http/public-playlists.test.ts`。
  - 预览与算法测试参考 `apps/songroom/src/operations/public-random-preview.test.ts`。
  - E2E 验收测试参考 `apps/songroom/tests/e2e/random-replacement.spec.ts`。

## Out of Scope

- 支持大于 50 首的超大批量抽选（避免网易云上游单次批量增删超时或触发风控 512 / RATE_LIMITED）。
- 支持小于 10 首的微型抽选（少于 10 首无法满足房间多成员均分听歌的协作价值）。
- 弹出软键盘由用户键入任意数字。
- 改造网易云两阶段批量替换（清空旧歌、批量添加新歌）的核心调度架构。

## Further Notes

- 每次打开“随机点歌”弹窗，首数选择器重置为 20 首，参与成员重置为全不选，必须由房主显式点击“生成预览”才触发数据加载与云端快照校验，严格遵守“操作显式驱动，严禁隐式抢跑”原则。
